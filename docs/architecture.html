Technikai architektúra

Otthoni sörfőző webapp: receptépítő élő számításokkal, BJCP stílusegyezés, főzőnap mód időzítőkkel, erjedéskövetés, kalibráció, vízkémia és költségszámítás – három nyelven, telepíthető PWA-ként, teljesen kliensoldalon, backend nélkül.

~900sor CSS (saját, framework nélkül)
4futásidejű függőség

Tervezési alapelvek

  • Statikus, kliensoldali app. Minden számítás a böngészőben fut, minden felhasználói adat a böngésző helyi tárolójában marad. Bármilyen statikus tárhelyen futtatható.
  • Tiszta számítási réteg. A src/lib függvényei mellékhatásmentesek: Recipe → Stats. A UI csak megjeleníti az eredményt, így a logika React nélkül, Node-ban is tesztelhető.
  • Minimális függőség. Nincs router, állapotkezelő, UI-könyvtár vagy grafikonkönyvtár – mindez néhány száz sor saját kód. Kisebb csomag, kevesebb frissítési teher.
  • Teljesítmény elsőként. A landing kicsi, a nehéz részek lusta betöltésűek és háttérben előtöltődnek; az animációk csak transform/opacity alapúak.
  • Adatvédelem alapból. Nincs harmadik féltől betöltött erőforrás (a betűtípusok is saját tárhelyről jönnek), szigorú CSP.

Architektúra

A belépési pont (src/main.tsx) egy kis hash-router. A landing azonnal betöltődik, a Főzőpult (App.tsx) és az adatvédelmi oldal külön csomagban, lustán érkezik. A számítási réteg és az adatok egy közös csomagban vannak, amelyet a Főzőpult és a landing receptszekciója is használ.

Útvonalak

Hash alapú útválasztás (location.hash + hashchange): statikus tárhelyen nem kell szerveroldali átírási szabály, és a PWA offline is minden útvonalat kezel.

Adatmodell és adatfolyam

A középpont a Recipe típus. A Főzőpult egyetlen useState<Recipe> állapotot tart; minden változáskor a computeStats() (memoizálva) újraszámolja a Stats-ot, amelyből az összes panel dolgozik. Nincs külön tárolt „számolt” állapot – minden levezetett érték mindig konzisztens.

Fő típusok (src/types.ts)

  • Malt, Hop, Yeast, Adjunct – katalógus tételek ízvektorral (FlavorVec)
  • BeerStyle – BJCP tartományok, élesztőtípusok, kötelező összetevők
  • Recipe – sorok (FermentableLine, HopLine, AdjunctLine), berendezés, víz, szénsav
  • BrewSession – recept-pillanatkép, mérések, időzítő, readings
  • Reading – erjedési mérés (idő, SG, hőfok, jegyzet)

Miért pillanatkép?

A BrewSession a főzés indításakor lemásolja a receptet. Így a napló és a kalibráció akkor is pontos marad, ha a receptet később módosítod – a mért értékek mindig ahhoz a változathoz tartoznak, amit ténylegesen megfőztél.

Többnyelvűség (i18n)

Kulcs = magyar szöveg

A felületen t('Hozzávalók') hívások vannak, helyőrzőkkel: t('{n} csomag', {'{'} n {'}'}). Előny: a kód olvasható marad, és hiányzó fordítás esetén is értelmes (magyar) szöveg jelenik meg, sosem üres. Az en.ts és a de.ts egyszerű Record<string, string>.

Adatfordítás azonosító szerint

A katalógus és a receptek leírásai (~200 tétel) a i18n/data.ts-ben vannak, td(fajta, id, mező, alapérték) olvassa. A márkanév nyelvenként eltér: Sörlabor / BeerLab / Bierlabor (lang.ts → BRAND).

  • Kétszintű betöltés: a lang.ts könnyű (nincs benne szótár), ezt használja a landing és az adatvédelmi oldal a saját kis szövegfájljával. A nagy szótárak csak a Főzőpult csomagjában vannak.
  • Nyelvváltás: a gyökérelem key={'{'}lang{'}'} attribútuma újrarajzolja a felületet; a memoizált számítások a nyelvet is függőségként kapják.
  • Formázás: dec() – angolul tizedespont, magyarul és németül vessző; dátum és pénz toLocaleString-gel.
  • Ellenőrzés: npm run i18n:check regexszel kigyűjti a t('…') kulcsokat és az adatokból a címkéket, majd kiírja a hiányzó és felesleges fordításokat (jelenleg 0 / 0, összesen ~800 kulcs).

PWA és offline működés

Workbox helyett egy kb. 80 soros saját Vite plugin (pwa-plugin.ts) a generateBundle fázisban legenerálja a sw.js-t:

  • Precache lista a build tényleges kimenetéből (minden JS/CSS csomag, manifest, ikonok, theme-init.js); a betűtípusokból csak a latin és latin-ext woff2 (12 fájl a 68-ból).
  • Verzió = a fájllista SHA-1 hash-ének eleje (pl. sorlabor-f6b7906b8b). Új build → új sw.js → új gyorsítótár, aktiváláskor a régi törlődik (skipWaiting + clients.claim).
  • Stratégiák: navigáció = hálózat először, offline esetén a gyorsítótárazott oldal; statikus fájlok = gyorsítótár először (a hash-elt fájlnevek miatt biztonságos).
  • A regisztráció csak éles buildben történik (import.meta.env.PROD), hogy ne zavarja a fejlesztői HMR-t.
// pwa-plugin.ts (részlet)
generateBundle(_opts, bundle) {
  const files = Object.keys(bundle).filter(/* .map és nem-latin betűtípusok nélkül */);
  const precache = ['./', ...files, ...extra];
  const version = createHash('sha1').update(precache.join('|')).digest('hex').slice(0, 10);
  this.emitFile({ type: 'asset', fileName: 'sw.js', source: serviceWorker(version, precache) });
}

Kiegészítők a lib/pwa.ts-ben: beforeinstallprompt elkapása és „📲 Telepítés” gomb (useInstallPrompt), online/offline jelző (useOnline). A manifest standalone módot, maskable ikonokat és parancsikonokat (Főzőpult, Receptek) definiál.

UI, témák, grafikonok

Témák CSS változókkal

Minden szín token (--bg, --surface, --accent, --accent-text…). A világos téma a :root[data-theme='light'] alatt írja felül őket; a „Rendszer szerint” mód a prefers-color-scheme-et követi. A theme-init.js még a React előtt beállítja a témát, így nincs villanás.

Kézzel írt SVG grafikonok

Ízprofil radar (9 tengely), erjedési görbék (SG és hőfok két külön diagramon – nincs kettős tengely), sörpohár a számolt színnel, pontszám-gyűrű, tartománysávok. Rámutatásra tooltip, role="img" + aria-label, és mellettük mindig van táblázatos nézet.

  • Animációk: csak transform és opacity (GPU-n komponálható), kivétel a landing pohár lassú színváltása. A hős szekció animációi IntersectionObserver-rel megállnak, ha nem látszanak; prefers-reduced-motion esetén minden animáció kikapcsol.
  • Görgetésre beúszás: IntersectionObserver + passzív görgetés-ellenőrzés tartaléknak, elemenként egyszer.
  • Bemutató (tour): saját komponens; a kiemelés négy sötétítő panel a kivágás körül (megbízhatóbb, mint egy óriás box-shadow), a pozíciót időzítő és görgetés-figyelő követi.
  • Számmezők: saját Num / OptNum – gépelés közbeni félkész értékek, vesszős tizedes, ↑/↓ léptetés, a sűrűség 1052 / 1,052 / °Plato formában is.
  • Reszponzív: CSS Grid, töréspontok 1100 / 900 / 720 / 620 px-nél; mobilon a főzőnap mód lépéslistája lenyíló.

Főzőnap mód: időzítők

  • Újratöltésbiztos időzítő: az időzítő nem számlálót, hanem időbélyegeket tárol (startedAt, elapsedMs) a BrewSession-ben, így oldal-újratöltés vagy a telefon lezárása után is pontos.
  • Riasztások: a forralási hozzáadások a hátralévő idő szerint sülnek el; a már elsütött és nyugtázott riasztások külön listában vannak, így semmi nem szól kétszer.
  • Hang: WebAudio oszcillátor (nincs hangfájl), első kattintásra „feloldva” a böngésző autoplay-szabálya miatt; mellette navigator.vibrate.
  • Értesítés: Notification API, ha a lap a háttérben van.
  • Képernyő ébren tartása: Screen Wake Lock API, láthatóság-váltáskor újrakérve.

Build, eszközök, ellenőrzés

ParancsMit csinál
npm run devVite fejlesztői szerver HMR-rel (SW nélkül)
npm run buildtsc -b típusellenőrzés, majd Vite build a dist/-be + sw.js generálás
npm run previewAz éles build helyi kiszolgálása (itt aktív a PWA)
npm run i18n:checkFordítás-ellenőrzés (hiányzó / felesleges kulcsok, adatfordítások)
  • base: './' és hash-router: a build bármilyen almappából, bármilyen statikus tárhelyről fut, szerveroldali beállítás nélkül.
  • Logika-tesztek: mivel a lib tiszta TypeScript, a fejlesztés során esbuild-del Node-ra bundle-ölt ad hoc szkriptek ellenőrizték a képleteket (pl. a 31 recept stílusegyezése, skálázás invarianciája, erjedési állapotfelismerés, költségszámítás).
  • Vizuális ellenőrzés: headless Edge képernyőképek (asztali és mobil szélesség, sötét és világos téma, három nyelv); a CSP-t fejléceket küldő helyi szerverrel és a konzolnapló figyelésével, egy szándékos szabálysértéssel kalibrálva.
  • Hosting: ajánlott a Cloudflare Pages (build: npm run build, kimenet: dist), részletek a README-ben.

Ismert korlátok, továbbfejlesztés

Korlátok

  • Nincs állandó automatizált tesztcsomag (a logika-tesztek ad hoc szkriptek voltak) – érdemes Vitestre átemelni.
  • A számítások becslések (ízprofil, cefre pH, energia); a katalógus árai és értékei tipikus, nem élő adatok.
  • Az adatok eszközhöz kötöttek: nincs szinkron gépek között (csak JSON export/import).
  • Az App.tsx nagy (~550 sor) – a fejléc és a modálok külön komponensbe szervezhetők.
  • A magyar szöveg mint fordítási kulcs: a magyar szöveg módosításakor a kulcsot az EN/DE szótárban is át kell írni (az ellenőrző jelzi).

Lehetséges következő lépések

  • Vitest egységtesztek a lib mappára, CI (GitHub Actions: típusellenőrzés, i18n, build, deploy).
  • Recept megosztása linkkel (a recept tömörítve az URL-ben, szerver nélkül).
  • Raktárkészlet és a bevásárlólista összekötése.
  • Opcionális szinkron (pl. EU-s backend-szolgáltatás) – ekkor bővíteni kell az adatvédelmi tájékoztatót.
  • Folyékony élesztők és starter-kalkulátor.
